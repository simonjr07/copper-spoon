# Database Design

## 1. Implemented foundation

Copper Spoon uses PostgreSQL 17 and Prisma ORM 7.10.0. Local PostgreSQL is defined in `compose.yaml`; the Prisma CLI is configured in `prisma7.config.ts`; `prisma/schema.prisma` is the application schema; and `prisma/migrations` is the reviewed SQL history.

Prisma 8 was not selected because its npm `latest` release is still a release candidate. Prisma 7 is the supported stable line for this foundation and uses the `@prisma/adapter-pg` driver adapter with `pg`.

The database stores timestamps as PostgreSQL `TIMESTAMPTZ(3)` values. Application code treats them as UTC instants and uses the configurable restaurant timezone—default `America/New_York`—only for display and operational date boundaries.

## 2. Money and identifiers

- All persisted money is integer USD cents: `$12.99` is `1299`.
- No persisted monetary column uses floating point or PostgreSQL decimal arithmetic.
- Internal primary keys are Prisma-generated CUID strings.
- `Order.publicCode` is a separate unique customer-facing code with a database format check for `CS-` plus 6–12 uppercase alphanumeric characters.
- Public codes are generated by the future order-creation service with cryptographically secure randomness and uniqueness retry; database counts are never exposed.

## 3. Enums

- `UserRole`: `ADMIN`, `STAFF`
- `UserStatus`: `ACTIVE`, `DISABLED`
- `OrderStatus`: `PENDING`, `CONFIRMED`, `PREPARING`, `READY`, `COMPLETED`, `CANCELLED`
- `FulfilmentType`: `PICKUP`, `DELIVERY`
- `PaymentMethod`: `PAY_ON_PICKUP`, `PAY_ON_DELIVERY`, `DEMO_CARD`
- `PaymentStatus`: `UNPAID`, `SIMULATED`, `SETTLED`
- `OptionSelectionType`: `SINGLE`, `MULTIPLE`

Payment fields model demonstration/restaurant workflow only. They do not represent processor-backed payments.

## 4. Models

### `User`

Credentials and staff authorization: normalized unique email, name, bcrypt-ready `passwordHash`, role, active/disabled status, last login, and timestamps. No users or credentials are seeded.

### `Category`

Unique slug, display content, non-negative `sortOrder`, publish state, timestamps, and one-to-many menu items.

`MenuItem.imageUrl` stores an optional display path. The current portfolio implementation uses repository-local `/images/menu/*.webp` paths; no asset-management schema or migration is required. Public DTO policy rejects remote, traversal-like, or unsupported paths and returns `null` for the UI fallback.

Task 8 required no schema migration. Existing `Order.status`, `updatedAt`, `completedAt`, and `cancelledAt` columns support the lifecycle and optimistic concurrency, while existing `OrderStatusEvent.fromStatus`, `toStatus`, `changedByUserId`, `note`, and `createdAt` columns provide the operational audit record. Status updates use a serializable transaction and a conditional current-row predicate before inserting the event.

### `MenuItem`

Category relation, unique slug, display content, `priceCents`, currency, optional image URL, ordering, publication, availability, archive state, timestamps, option groups, and optional historical order-item references.

Categories are delete-restricted while menu items refer to them. Application behavior archives catalog data rather than destructively deleting records used operationally.

### `MenuItemOptionGroup`

Belongs to a menu item and defines a named `SINGLE` or `MULTIPLE` choice, minimum/maximum selections, ordering, active state, and timestamps. The database enforces non-negative minimum, positive maximum, `min <= max`, and a maximum of one for `SINGLE` groups.

### `MenuItemOption`

Belongs to an option group and contains a name, non-negative price adjustment in cents, ordering, availability, and timestamps. Names are unique within their group.

### `Order`

Contains internal ID, nullable unique `checkoutToken`, unique `publicCode`, lifecycle/payment/fulfilment state, customer contact, snapshotted delivery address, customer note, currency, subtotal/delivery/total cents, operational timestamps, items, and status events. New checkout orders use a UUID checkout token for retry idempotency; null preserves compatibility with earlier/administratively-created rows.

Database checks require:

- a version-4 UUID shape when `checkoutToken` is present;
- normalized customer email;
- a complete line 1/city/postal code/country snapshot for delivery;
- pay-on-pickup only with pickup and pay-on-delivery only with delivery;
- non-negative amounts and `totalCents = subtotalCents + deliveryFeeCents`;
- zero delivery fee for pickup.

### `OrderItem`

Belongs to an order and optionally references the current menu item. Historical fields—`itemNameSnapshot`, `unitPriceCentsSnapshot`, `quantity`, `optionsTotalCentsSnapshot`, and `lineTotalCents`—are authoritative. A check requires a positive quantity and verifies the stored line-total equation.

### `OrderItemOption`

Belongs to an order item and optionally references the current catalog option. It snapshots the option-group name, option name, and non-negative price adjustment.

### `OrderStatusEvent`

Append-oriented history containing order, optional previous status, next status, optional staff actor, safe note, and timestamp. Initial creation may have a null previous status; other events cannot record the same from/to status.

### `RestaurantSettings`

A database check restricts the table to the fixed ID `restaurant-settings`, giving the single restaurant one settings row. It stores restaurant/contact/address basics, USD, configurable timezone, pickup/delivery and demo-payment switches, and non-negative delivery amounts.

## 5. Relationship and deletion behavior

```text
Category 1 --- * MenuItem
MenuItem 1 --- * MenuItemOptionGroup
MenuItemOptionGroup 1 --- * MenuItemOption
Order 1 --- * OrderItem
OrderItem 1 --- * OrderItemOption
Order 1 --- * OrderStatusEvent
User 1 --- * OrderStatusEvent (optional actor)
```

Order-owned children cascade only with deliberate order deletion. Catalog references on immutable order snapshots become null if the referenced item/option is removed, preserving the snapshot. Staff deletion sets the status-event actor reference to null. Normal product behavior disables/archives instead of deleting history-bearing records.

## 6. Snapshot invariant

If a burger is ordered at `1450` cents with a `150`-cent cheese option and later changes price/name, the order continues to use:

```text
OrderItem.itemNameSnapshot
OrderItem.unitPriceCentsSnapshot = 1450
OrderItem.optionsTotalCentsSnapshot = 150
OrderItem.lineTotalCents
OrderItemOption.optionGroupNameSnapshot
OrderItemOption.optionNameSnapshot
OrderItemOption.priceAdjustmentCentsSnapshot = 150
```

Historical display and analytics must never join current catalog pricing to recalculate these values.

## 7. Transactional order creation contract

The implemented checkout service performs, in one serializable database transaction:

1. Resolve an existing unique checkout token for idempotent retries.
2. Load and validate current settings, published/available items, and valid options.
3. Calculate all cents values on the server, including the current settings delivery fee.
4. Generate and reserve a cryptographically random non-sequential public code, retrying uniqueness/serialization conflicts.
5. Create the order, immutable item/option snapshots, and initial `PENDING` status event through one nested write.

Stale or unavailable cart data rejects the whole operation. Client-provided prices/totals are ignored.

Migration `20260928000000_order_checkout_idempotency` adds only the nullable checkout token, its UUID-format check, and unique index. No catalog or historical-order data is rewritten.

## 8. Indexes

Indexes cover unique staff email, catalog slugs, public order code, staff role/status, published menu ordering, available option ordering, recent orders by status/time, order children, status-event timelines, and nullable audit/catalog references. New indexes require a demonstrated query pattern or query-plan evidence.

## 9. Local workflow

```bash
Copy-Item .env.example .env
docker compose up -d postgres
npm run db:validate
npm run db:generate
npm run db:migrate
npm run db:seed
npm run db:smoke
```

Change the local password in both `POSTGRES_PASSWORD` and `DATABASE_URL`. On macOS/Linux, use `cp .env.example .env`. Stop the service with `docker compose stop`; use `docker compose down` without `-v` to retain the named database volume.

The Compose mapping is `127.0.0.1:5433` on the host to PostgreSQL port `5432` inside the container, so the local `DATABASE_URL` uses `localhost:5433` without exposing the database beyond the local machine.

`db:migrate` is for local development. `db:deploy` applies already-reviewed migrations in deployment environments. Never run reset or volume-removal commands against an unverified target.

## 10. Migration and seed policy

- The initial migration includes foreign keys, indexes, enum types, and custom PostgreSQL checks not expressible in the Prisma schema.
- Every later schema change includes a reviewed migration and corresponding tests/docs.
- Seed execution is explicit in Prisma 7 (`npm run db:seed`); migration commands do not seed automatically.
- The seed is idempotent for its known slugs/names and creates only fictional restaurant settings, five categories, seven menu items, local WebP image paths, and representative options. One published dessert is deliberately sold out to exercise the public availability state. It never creates a staff user or credential.
- Generated Prisma Client is excluded from Git and recreated by `postinstall`/`db:generate`.

## 11. Integration testing direction

Database integration tests will use a positively identified, isolated PostgreSQL database, apply migrations, and exercise transactions/constraints. The first behavior-heavy suite lands with checkout/order creation; the current `db:smoke` command verifies connection and seeded catalog/settings without mutating data.
